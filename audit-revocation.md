## Что изменено

- Перед доставкой WS-события сервер получает актуальное членство из PostgreSQL. Старые registry-подписки и доставка `member.leave` через Redis больше не являются источником разрешений. Проверяются также адресные уведомления с привязкой к серверу/каналу.
- Строки членства блокируются `FOR SHARE` до синхронной постановки WS-сообщения в сокет. Удаление членства сериализуется с этой границей отправки. Уже отправленные или находящиеся в сети байты отозвать нельзя.
- Потенциально устаревший `hello` проверяется повторно перед добавлением соединения и отправкой `ready`; исключаются отозванные серверы и каналы. Закрытое соединение не регистрируется заново. Аналогичная проверка добавлена в hot-attach.
- Kick/leave после транзакции закрывают все локальные соединения пользователя, перед закрытием отправляя контрольное уведомление. Другие процессы проверяют БД при отправке и периодически сверяют неактивные подписки. Очередь доставки ограничена 128 событиями: при переполнении соединения закрываются, а не получают непроверенные данные.
- Входящие `typing`/`presence` проверяются по актуальному членству. Ошибки асинхронной обработки перехватываются. Это ephemeral-события, не транзакционные REST-мутации.
- Kick/leave вызывают удаление всех устройств пользователя во всех голосовых каналах сервера. Ошибка одного удаления не скрывается и не мешает попыткам остальных. Успехом считается только явный Twirp `not_found`, а не произвольный HTTP 404 прокси.
- Если SFU-удаление не удалось, членство остаётся удалённым, HTTP возвращает `503 voice-revocation-pending` с понятным сообщением. Успех `204` не выдаётся. Периодический обход реальных LiveKit-комнат повторяет удаление; отсутствие членства в БД переживает перезапуск процесса и служит состоянием для повтора. Учитываются комнаты, чей канал/сервер уже удалён из БД.
- Проверка доступа для `participant_joined`/изменений треков выполняется после проверки подписи webhook, но до дедупликации. Ошибка удаления оставляет событие повторяемым и возвращает 503. `userId:deviceId` нормализуется до userId и при публикации `voice.join`.
- Выдача voice-токена повторно проверяет доступ после асинхронной подготовки ответа. Начальный TTL снижен до 60 секунд; это уменьшает срок использования неиспользованного токена, но **не заменяет отзыв токенов**. Server API LiveKit получает таймаут запроса 3 секунды.

## Оставшийся блокер 3-B: admission/reconnect

У self-hosted LiveKit удаление участника не отзывает существующий JWT. Токены также обновляются самим LiveKit: снижение начального TTL не даёт верхней границы доступа для уже подключавшегося клиента. Документация: [LiveKit tokens and grants](https://docs.livekit.io/frontends/reference/tokens-grants.md), раздел Token revocation.

Текущие webhook/reconciliation удаляют нарушителя **после входа**. Интервал обхода 5 секунд — не гарантия максимальной задержки: влияют нагрузка, число комнат, ожидание БД и доступность SFU. При отказе SFU отключение не может быть гарантировано. Ручной audio/video/RTP-прогон, TURN и длительные reconnect-сценарии не выполнялись.

Для строгого закрытия нужен согласованный архитектурный шаг:

1. Предпочтительно сохранить self-hosted: спроектировать доверенную границу допуска/повторного подключения, согласованную с отзывом членства и фактическим входом в SFU. Закрыть возможность обхода этой проверки прямым signaling-доступом.
2. Нельзя объявлять решение полным, просто добавив одноразовый `forward_auth` перед reverse proxy: остаётся гонка «проверка разрешена → kick → фактический вход в SFU». Нужны сериализация/версионирование допуска, поведение при сбоях и тесты всех путей reconnect.
3. Альтернатива — сервис/SFU с поддерживаемым отзывом токенов. Миграция, оплата, изменение сети или production-конфигурации без отдельного решения не выполняются.

### Критерий закрытия 3-B

Старый и обновлённый JWT исключённого пользователя не дают получить новые аудио/видео/данные; одновременный join/reconnect не обходит kick. Проверить два устройства, независимые процессы, потерю webhook/Redis-событий, перезапуск, отказ БД/SFU, прямой обход прокси и штатный доступ остальных участников. После реализации заменить ожидание успешного replay в характеризационном тесте на обязательный отказ.
