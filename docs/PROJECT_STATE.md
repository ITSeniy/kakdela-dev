## Краткий вывод

«КакДела» — self-hosted мессенджер для компании из 15–20 друзей. Версия пакетов — **0.8.0**. Код уже существенно шире исходного MVP: кроме серверных чатов, голоса и демонстрации экрана есть DM, треды, роли, медиа, мобильная оболочка и секретные чаты.

Последний содержательный этап — исправления безопасности и надёжности, особенно отзыв доступа к WebSocket и LiveKit. TypeScript и web-сборка проходят, обычные тесты зелёные. При этом аудит остаётся закрыт частично, а документы о фазах отстают от реализации.

### Основные потоки

- Сообщения и другие сохраняемые изменения идут через REST; WS доставляет события клиентам. WS также принимает `hello`, ping/pong, typing и presence: описание «receive-only» в `CLAUDE.md` является упрощением.
- Серверные данные на клиенте обслуживает TanStack Query; состояние интерфейса и части сессии — Zustand. Нативные операции сосредоточены в `polly/src/lib/host/`.
- Голос/видео передаются через LiveKit. Публичная сигнализация теперь идёт через speedy `/livekit`, а административный SFU остаётся приватным.
- Загрузка файлов: presign → прямой PUT в MinIO → finalize с проверкой содержимого и обработкой изображения → привязка к сообщению. URL вложений пока публичные.
- Секретные чаты: сервер хранит публичные prekey и зашифрованные конверты; libsignal и локальная история находятся на нативной стороне. Для Android сохранение ключа через Keystore ещё не реализовано: `sealed.rs` возвращает `keychain-unavailable`.

### Важные свойства новой защиты

- Источник прав — PostgreSQL, а не локальный registry или событие Redis. См. `speedy/src/ws/access.ts` и `speedy/src/media/admission-access.ts`.
- Gateway выдаёт отдельные tickets, создаёт SFU-сессию с ограниченными правами и повышает права под блокировкой членства. Сигнализация раскрывается после успешного COMMIT.
- Каждый новый вход и полный reconnect проверяет доступ заново; быстрый resume отключён.
- При удалённом членстве и неуспешной SFU-очистке API возвращает `503/pending`, а не ложное подтверждение `204`.
- По последнему сохранённому отчёту шлюз **не включён на рабочем окружении**. Для включения необходимы согласованные версии клиента/backend/Caddy, закрытый прямой SFU signaling и завершение старых прямых сессий. Проверки кода сами по себе этого не подтверждают.

## Документация, которую стоит синхронизировать

1. **`README.md`:** предлагает `npm install` и `npm test`, хотя проект использует pnpm/workspace-протокол, а корневого `test`-скрипта нет. Рабочая команда тестов — с фильтром speedy.
2. **`README.ru.md`:** указывает Node 20+ и MSI; текущие требования — Node 24, Windows bundle настроен на NSIS. Для native-сборки также нужен `protoc` — это описано в `CLAUDE.md`.
3. **`.claude/CURRENT_PHASE.md`:** мобильная фаза названа запланированной, хотя её код и частично/полностью отмеченные карточки T-100…T-103 уже существуют. T-089/T-090 указаны незавершёнными, но профильные поля, роли, endpoints и UI присутствуют; нужно сверять оставшийся DoD, не реализовывать повторно.
4. **`tasks/README.md`:** говорит о 50 задачах, сейчас файлов T-*.md — 68.
5. **Правила auth/WS:** запрет auth в Zustand расходится с `features/auth/store.ts`, где access token хранится в памяти. `host/secrets.ts` выбирает keychain/IndexedDB AES-GCM/sessionStorage с fallback; формулировка «web только sessionStorage» неточна. Комментарий в начале `secrets.ts` также описывает направление миграции иначе, чем `osSecrets.get`, который переносит legacy IDB → keychain.

При следующей задаче проверять реализацию и актуальные audit-документы вместе с карточкой. Старые сводки сохраняют полезный замысел, но не дают достоверной картины завершённости.
