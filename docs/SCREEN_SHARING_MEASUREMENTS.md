# Демонстрация экрана: подготовка и замеры

Реализация 2026-09-15 после [анализа](SCREEN_SHARING_ANALYSIS.md). Исправления и инструменты внесены в клиент; фактическое качество на двух desktop-клиентах ещё не измерено. P2P и обновление LiveKit не входят в этот этап.

## Что изменено

- Ограничения screen share передаются через `screenShareEncoding`. Capture и sender получают согласованные FPS; пресеты больше не наследуют скрытые 15 fps.
- Профили **текст и работа** / **игры и видео** задают `maintain-resolution` / `maintain-framerate` соответственно. VP9 в SDK 2.19 всё ещё использует workaround `motion + L1T3`; он намеренно не переписан.
- Новый пользователь начинает с «1080p · по профилю»: текст — 30 fps / 5 Мбит/с, движение — 60 fps / 10 Мбит/с. Существующий выбор качества сохраняется. Это фиксированный профиль, не автоматическая оценка сети/GPU.
- Доступны 1440p30, 1080p60/30, 720p60/30/15. Настройки применяются при следующем запуске демонстрации.
- Кодек выбирается в дополнительных настройках: VP9 (по умолчанию) или H.264. Для сравнения используется один encoding, без simulcast/backup codec. Аппаратное ускорение не гарантируется; фактический кодек смотреть в диагностике.
- Повторные попытки снимают аудио/ограничения захвата, сохраняя publication options. В последнем запасном пути SDK может взять свой capture 1080p30 даже при выбранном 60 fps; поэтому отдельно видны захват и отправка. Отмена picker, занятый источник и сетевые ошибки не вызывают новые попытки.
- Browser screen audio и WASAPI публикуются с явным stereo Opus, 128 кбит/с, DTX off, RED on. Микрофонные defaults сохранены. Отказ публикации/смена демо освобождает созданный native audio handle.
- Бейдж демо обновляется примерно раз в 2 секунды. По клику открываются измерения и копирование JSON за последние 5 минут. История находится только в памяти текущей плитки; закрытие/перемонтирование плитки или смена трека начинает её заново.

Основные исходники: [настройки](../packages/polly/src/features/voice/screen-share-config.ts), [повторные попытки](../packages/polly/src/features/voice/screen-share-start.ts), [статистика](../packages/polly/src/features/voice/screen-share-stats.ts), [панель](../packages/polly/src/features/voice/ScreenShareDiagnostics.tsx).

## Локальная проверка реализации

Из корня репозитория, Node 24 / pnpm 9.12.0:

```sh
pnpm --filter @kakdela/polly test:screen-share
pnpm --filter @kakdela/polly typecheck
pnpm --filter @kakdela/polly build
```

8 регрессионных тестов: расчёт всех профилей/кодеков через **установленный SDK**, stereo defaults, сохранение настроек в fallback, отмена/ошибки, дельты статистики, reset/stall, неизвестные поля и исключение сетевых адресов из экспорта. Код тестов: [screen-share.test.ts](../packages/polly/tests/screen-share.test.ts).

Проверены браузерный интерфейс пикера, переключение профилей, сохранение выбора после перезагрузки, раскрытие диагностики и копирование отчёта на синтетических данных. Это проверка UI, не результат медиазамеров. Web build не подтверждает native-сборку Tauri, WASAPI или передачу stereo получателю.

## Первый сеанс: два desktop-клиента

1. Запустить обновлённый клиент у автора и зрителя. Для локальной разработки — `pnpm dev:polly` после настройки окружения из [DEVELOPMENT](DEVELOPMENT.md); для установленного приложения нужна новая native-сборка. Старая установленная версия не меняется после web build.
2. Зафиксировать Windows/WebView2, CPU/GPU, размер и масштаб экрана, подключение Wi-Fi/Ethernet, число зрителей. Выбрать одинаковый контент и область окна для всех сравнений.
3. Начать с одного зрителя, который нажал «смотреть». Раскрыть обе плитки: маленькие компактные превью статистику не собирают. Не менять раскладку во время одного прогона.
4. После начала передачи дать соединению 10–15 секунд. Каждый вариант проверять 60–90 секунд. После прогона **до остановки демо** нажать бейдж → «копировать последние 5 минут» на обеих сторонах и сохранить JSON отдельно как sender/viewer с названием прогона.
5. Остановить демо перед сменой профиля/кодека. Повторить тот же контент; не сравнивать разные сцены игры или разные размеры окна как A/B одного кодека.

| Прогон | Настройки | Контент и наблюдения |
|---|---|---|
| 1 | Текст, 1080p30, VP9 | IDE/страница с мелким текстом: 20 с покоя, 20 с скролла, затем перемещение окна |
| 2 | Текст, 1440p30, VP9 | Та же область на источнике не ниже 1440p; сравнить читаемость и нагрузку |
| 3 | Движение, 1080p30, VP9 | Повторяемое видео/сцена с постоянным движением |
| 4 | Движение, 1080p60, VP9 | Тот же фрагмент с исходными 60 fps; проверить CPU/GPU и пропуски |
| 5 | Движение, 1080p60, H.264 | Сравнить с прогоном 4; убедиться в фактическом кодеке по статистике |
| 6 | Текст, 1080p30, H.264 | Сравнить с прогоном 1: детали текста, bitrate и encode time |
| 7 | Выбранные лучшие профили | Повторить с 2 и 5 зрителями, затем в DM 1:1 и в голосовой комнате |

Если 1080p60 перегружает устройство, проверить 720p60 и 1080p30. Для экономного режима — 720p15. Поведение на ограниченной полосе/через TURN проверить отдельными прогонами после базового теста.

## Как читать показатели

- **Отправка / приём**: resolution берётся из RTP stats, FPS — из разности encoded/decoded frames за интервал. При отсутствии счётчиков используется framesPerSecond, если браузер его предоставляет. Отсутствующие значения показаны «—», а не нулём.
- **Захват**: размеры и согласованная настройка frameRate из getSettings, не доказательство такого числа отправленных кадров. В JSON эта настройка называется `capture.requestedFps`.
- **Локальное превью / показ видео**: скорость продвижения счётчика воспроизведённых кадров video-элемента. Локальное preview может быть плавным при низком FPS отправки.
- **Битрейт**: дельта bytesSent/bytesReceived за интервал; первый отсчёт неизвестен. Это RTP-показатель трека, не весь сетевой трафик приложения.
- **Кодирование / декодирование**: среднее время на кадр за интервал. Сравнить с бюджетом 33,3 мс при 30 fps / 16,7 мс при 60 fps. Дополнительно смотреть CPU/GPU в диспетчере задач.
- **Ограничение cpu/bandwidth** относится к отправителю и его пути до SFU. Оно не доказывает перегрузку VPS. У зрителя это поле может отсутствовать.
- **RTT / путь**: текущий ICE-путь этого клиента до SFU, не end-to-end задержка картинки. `relay` означает TURN; поля могут отсутствовать в sender/receiver stats конкретного WebView2.
- Потери, NACK, PLI, пропущенные кадры и замирания — накопительные счётчики текущего потока. Для сравнения брать прирост за одинаковый интервал. Браузер может менять stats ID при переподключении; дельты при сбросе не рассчитываются.
- **Буфер**: средняя задержка jitter buffer на интервале. Значение бывает только у получателя.

Низкий FPS на неподвижном тексте допустим: отсутствие изменений не требует постоянных одинаковых кадров. Проверку 30/60 fps проводить на движущемся источнике. Для оценки end-to-end задержки нужен синхронизированный таймер в кадре или внешнее измерение; не подменять её RTT.

## Звук и жизненный цикл

- Проверить поочерёдный звук в левом/правом канале на стороне зрителя, затем речь + музыка/видео. Убедиться, что микрофон работает как раньше.
- Проверить звук выбранного окна, всей системы и «без звука», отсутствие эха/дублирования, синхронность хлопка/вспышки.
- Отмена системного picker, повторный start/stop, остановка из OS bar, выход из комнаты, reconnect и отзыв доступа должны останавливать видео/звук без зависшего захвата.
- Повторить отказ/недоступность browser audio и Windows native audio. Очередь PCM и её дрейф пока не инструментированы; при нарастающей задержке это отдельная гипотеза из исходного анализа.

## Решение после замеров

Выбрать defaults по читаемости, плавности, encode/decode time и загрузке CPU/GPU на целевых устройствах. Только после этого оценивать пользу P2P 1:1: выигрыш сетевого пути сравнивать с исправленным SFU. Групповой SFU и существующие гарантии admission сохраняются на этом этапе.
