# Аудит: пакет 3-B — admission gateway для LiveKit

Дата: 2026-09-07–08. Продолжение [пакета 3-A](audit-revocation.md).

## Результат и границы

Реализован шлюз, который проверяет актуальное право на голосовой канал при каждом новом подключении и полном reconnect. Старый, legacy-SFU или обновлённый токен сам по себе больше не даёт доступ после удаления членства. Это не замена SFU и не переход с self-hosted LiveKit.

**Локальная реализация и испытания не означают включённую защиту на VPS.** Рабочие сервисы не перезапускались; настоящий `.env`, рабочая БД, данные, MCP-аутентификация и удалённые Git-ветки не менялись. Требуется отдельное развёртывание по порядку ниже.

## Как устроена граница доступа

1. Публичный `LIVEKIT_URL` указывает на `/livekit` в speedy через Caddy. SFU signaling/admin-порт 7880 не доступен пользователям напрямую. UDP/TCP медиапорты остаются у SFU.
2. API выдаёт gateway-ticket: HS256, отдельные issuer/audience и ключ, полученный HMAC-SHA256 от SFU-секрета с контекстом `kakdela/livekit-admission/v1`. SFU и app-auth не принимают этот билет как свой JWT. Начальный TTL — 60 секунд.
3. Gateway принимает ровно один credential: `access_token` либо `Authorization: Bearer`. Проверяются подпись, алгоритм, срок, UUID пользователя и имя комнаты. Legacy LiveKit JWT разрешён **только как входной credential**; пересылки клиентского JWT на SFU нет.
4. Первая проверка PostgreSQL отсекает удалённых участников до создания SFU-сессии. Для `voice-*` проверяются вид канала и членство на сервере; для `dm-*` — настоящий DM-канал и одна из двух сторон разговора.
5. На SFU создаётся новая bootstrap-сессия с `canPublish=false`, `canSubscribe=false`, `canPublishData=false`, `canUpdateOwnMetadata=false`. Gateway не выдаёт клиенту JoinResponse/SDP и не пересылает клиентские сигнальные сообщения, пока проверка не завершена.
6. Получив bootstrap JoinResponse, gateway повторно проверяет доступ с `FOR SHARE` на канале и членстве. В той же транзакции вызывает SFU `updateParticipant`, проверяет SID, identity и выданные разрешения. Удаление членства при kick/leave ждёт освобождения этой блокировки.
7. Буфер сигнализации раскрывается **только после успешного COMMIT**, а не внутри callback транзакции. При ошибке RPC, обрыве БД, закрытии клиента или таймауте доступ не открывается. Даже поздно выполненный RPC не даёт недопущенному клиенту SDP/DTLS-данных для этого транспорта.
8. Обновления SFU-токена заменяются gateway-ticket с TTL 600 секунд. Реальный SFU JWT клиенту не раскрывается. Первый SFU refresh ещё может содержать bootstrap-права; билет сохраняет исходный разрешённый scope. Новый вход всегда проверяет БД заново.
9. Быстрый resume старого транспорта отключён. SDK получает `resumeConnection=DISABLED`; явный запрос resume переводится в полный reconnect без передачи `sid` на SFU. `/rtc/v1` намеренно возвращает 404: SDK делает fallback на V0. SDP в `join_request`, подмена identity/metadata и `publish`-override не проходят.
10. UUID приводятся к нижнему регистру, device suffix сохраняется. Это устраняет разницу между сравнением UUID в PostgreSQL и чувствительными к регистру именами SFU-комнат/участников. Kick с UUID в верхнем регистре также нормализуется.

Локальное закрытие gateway-сокетов ускоряет отзыв; Redis pub/sub не является источником разрешения. Межпроцессная защита использует PostgreSQL и SFU RPC. Повторное предоставление членства — новое законное основание доступа: это не система вечного blacklist для каждого ранее выданного JWT.

## Отказы и ограничения

- `204` после kick/leave означает, что завершилась предусмотренная SFU-очистка всех устройств. Если SFU недоступен, membership уже удалён, но ответ — `503`/отзыв ожидает повторной попытки 3-A. **Мгновенная остановка RTP при недоступном SFU не обещается.**
- Gateway admission имеет предел 8 секунд; upstream handshake — 4 секунды; административный SDK RPC — 3 секунды. В транзакции заданы `statement_timeout=3s` и `idle_in_transaction_session_timeout=10s`.
- Защита буферов: до 128 кадров и 1 MiB на направление до допуска; ограничение backpressure. Входной websocket speedy дополнительно ограничен 64 KiB на кадр. Лимиты gateway: 64 соединения на процесс, 12 на IP, 10 на пользователя. За общим NAT лимит IP может потребовать пересмотра; `TRUST_PROXY` должен доверять только настоящему reverse proxy.
- Для SFU JWT допускается рассинхронизация часов до 30 секунд, для gateway-ticket — нет. В локальных испытаниях часы Docker опережали Windows примерно на 20 секунд. На VPS необходима синхронизация часов; большие расхождения не маскируются.
- Самостоятельно открытый SFU signaling-порт или старое прямое signaling-соединение обходит gateway. Это обязательное условие развёртывания, а не опциональная настройка.
- Полный reconnect вместо resume может давать более заметную паузу звука. Не реализован отдельный UX-индикатор отказа admission.
- Испытания не заменяют проверку реального Tauri/browser-клиента на VPS, TURN/NAT, screen sharing и восстановление при переключении сети.

## Журналы и воспроизводимость

В speedy query string удаляется из request-логов, стандартный 404 заменён безопасным обработчиком без сырого URL в `msg`; gateway не логирует исходные SDK-ошибки, JWT и upstream bodies. В Caddy runtime/error-логах удаляются URI и headers запроса. Не следует добавлять необработанные access/debug-логи поверх этого контура.

LiveKit закреплён в dev/prod compose и тестах по проверенному digest:

```text

## Проверки

Итоговый прогон и хеши файлов сохранены локально в `.git/admission-20260907/`. Не добавляются в Git: шумные логи, временные credentials, сырые сигнальные сообщения.

- Обычные тесты: 94, включая 16 новых сценариев JWT и 2 проверки безопасного логирования.
- Существующие PostgreSQL-интеграции 3-A: 29 сценариев.
- Admission: 17 сценариев с настоящими PostgreSQL и LiveKit, двумя отдельными Node-процессами, потерянным pub/sub, restart/reconnect, replay initial/legacy/refreshed tickets, канонизацией UUID, DM, query/header ambiguity, буферизацией и отказами.
- Отдельно проверяется реальное `pg_terminate_backend` после успешного SFU elevation: JoinResponse/SDP не выходят к клиенту.
- Сквозной аудиосценарий входит в 17: официальный Node RTC SDK, синтетический тон 440 Hz без микрофона/динамиков, WebRTC/UDP на loopback; до kick принимаются декодированные ненулевые кадры, после `204` счётчик доставки перестаёт расти, другой участник остаётся на SFU. Это функциональный тест штатного SDK, не имитация всех вариантов вредоносного RTP-клиента.
- Отдельная SFU-characterization: 2 сценария. Public ticket отвергается прямым SFU; специально выданный legacy JWT всё ещё повторно входит при **намеренном обходе gateway внутри одноразового стенда**. Этот тест объясняет запрет публичного 7880 и не считается исправлением самого LiveKit.
- Дополнительно: frozen lockfile, typecheck всего workspace и новых тестов, lint/build, dependency audit, валидация Caddy и обоих compose-наборов — успешно. Lint: 0 ошибок, 13 прежних предупреждений; остаётся предупреждение Vite о размере bundle. `pnpm audit` не нашёл известных уязвимостей на момент проверки. Нативная сборка Tauri и Docker build в 3-B повторно не запускались.

Повторить на Node 24 / pnpm 9.12.0 с Docker:

```sh
pnpm install --frozen-lockfile

Runners создают именованные одноразовые контейнеры, используют синтетические секреты и случайные loopback-порты, не монтируют рабочие тома и удаляют свой стенд в `finally`. CI дополнен этими проверками; запуск в GitHub не выполнялся, push не делался.

## Порядок включения на рабочем окружении — вручную

1. Подготовить согласованный комплект speedy/Caddy/клиента и закреплённый SFU. В dev установить `LIVEKIT_URL=ws://localhost:3001/livekit` и соответствующий `VITE_LIVEKIT_URL`; admin URL остаётся `http://127.0.0.1:7880`. Старый dev URL на `:7880` теперь намеренно не проходит startup-validation.
2. В prod использовать `LIVEKIT_URL=wss://<домен>/livekit`, `LIVEKIT_ADMIN_URL=http://livekit:7880`. Проверить, что Caddy `/livekit/*` направлен исключительно в speedy, не stripping prefix и не fallback на SFU/twirp.
3. Проверить извне firewall/ports: SFU 7880 и административные API недоступны, включая альтернативные хосты/IPv6. LiveKit secrets не выдаются пользователям; разрешены только нужные медиапорты.
4. В согласованное окно закрыть старые прямые signaling/медиасессии — например, управляемым перезапуском SFU после переключения маршрутов. Одного reload Caddy или замены URL недостаточно: существующий DTLS-транспорт иначе остаётся за пределами новой границы.
5. Проверить двумя учётными записями: voice и DM, несколько устройств, kick и leave, replay сохранённого токена, полный reconnect, screen sharing, TURN/NAT. После успешного отзыва исключённый участник не должен вернуться до нового предоставления членства.
6. При откате не открывать прямой SFU как временный обход. Безопаснее временно отключить голосовые подключения и восстановить согласованный комплект.

До выполнения этого порядка статус production-защиты остаётся «не развёрнуто».
